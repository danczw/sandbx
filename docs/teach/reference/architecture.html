Architecture cheat sheet

28 crates, six layers, two roads to the filesystem. As of 0.1.0-alpha.27.

The one-sentence version

A CLI drives a turn loop that streams from the model's API; each tool call passes an offered-tools check and an approval gate, then either runs in-process under FsGuard (six tools) or, for bash, in a re-exec'd helper that locks itself with Landlock, seccomp and namespaces before running the command.

Two roads

read/write/edit/ls/grep/find ──► FsGuard (in-process) ──► never reaches Landlock
bash                         ──► helper re-exec       ──► Landlock + seccomp + netns

Both derive from one table, Axis::grants() in sandbox_policy.rs, so they cannot answer one policy differently.

Path of a bash call

  1. main → with_helper_dispatch: am I the helper? (before flag parsing)
  2. sandbx-cli parses flags; sandbx-grants builds the policy
  3. sandbx-turn streams a round from sandbx-anthropic
  4. Tool call: known name? offered this turn? → else refused before the gate
  5. CallGate::approve (ArgvGate for agent-run, Gate in tui.rs)
  6. sandbx-tools: /bin/sh -c CMD as a SandboxedCommand
  7. sandbx-core re-execs /proc/self/exe --sandbx-core-exec …
  8. Helper locks itself, runs the shell; output capped and returned; audit on stderr

Enforced by the build

  • unsafe forbidden in every crate.
  • Command::new banned by clippy.toml; only sandbx-core's spawn::command may spawn.
  • deny.toml: which crate may depend on which; only sandbx-anthropic may use reqwest; nothing may depend on sandbx-cli.
  • Limit: convention plus tooling. Sees only sandbx's own code, not its dependencies.
