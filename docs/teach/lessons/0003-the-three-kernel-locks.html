The three kernel locks

One namespace you haven't met: the user namespace

Making namespaces normally needs root. A user namespace is the exception: an ordinary user may create one, and inside it the process counts as privileged for that namespace only.

the process has full privileges for operations inside the user namespace, but is unprivileged for operations outside the namespace. user_namespaces(7)

That is what lets sandbx create the others without being root, and it is why the README requires "unprivileged user namespaces". Which namespaces a command gets:guide-sandboxing:395

  • user and PID: always, whatever the policy;
  • network: unless network is granted in any form;
  • mount: only with --allow-dns, for the private /etc files.

The capability sets from row 8 are emptied so that "privileged inside its own namespace" does not turn into real powers.

The new idea: the locks guard each other

Each lock has a blind spot, and in every case another lock covers it. This is the answer to "why three?":

WeaknessCovered by
Landlock's rules are tied to the file tree, and a mount or pivot_root could move the tree out from under themseccomp blocks every mount routeSECURITY:81
Landlock matches on paths, and memfd_create makes a file that has no pathseccomp blocks memfd_createSECURITY:528

A command could build itself new namespaces to escape the ones it is inseccomp blocks namespace creation on every routeSECURITY:79

And one prerequisite under both: no_new_privs. A process without admin rights can install neither seccomp nor Landlock until that flag is set, so it comes first in the setup.guide-sandboxing:151

Analogy

A bank vault has a door, a guard and cameras. The guard stops anyone from unscrewing the door. The cameras catch whatever the guard cannot see. Take any one of them away and the other two each gain a hole.

The environment is a fourth bound that none of the three can reach: the kernel hands it over when a program starts, before any lock applies. So it is enforced by not passing it.

Drill 1: which lock did that?

Each line is something you would see from inside the sandbox. Pick the lock responsible. "Other" covers anything none of the three does.

  1. With default flags, cat /etc/shadow gets "permission denied".
  2. The command runs mount -t tmpfs none /tmp/x and gets EPERM.
  3. With no network flag, curl https://example.com can't connect to anything.
  4. A background sleep 1000 & is gone the moment the call ends.
  5. Under --allow-network 443, creating a UDP socket fails.
  6. Under --allow-network 443, connecting to port 22 fails.
  7. Your shell's GITHUB_TOKEN doesn't appear in env.
  8. Calling io_uring_setup returns EPERM.
  9. A program under an --allow-read path refuses to start.
  10. A 32-bit syscall from a 64-bit program kills the process.
  11. Under --allow-dns example.com, github.com doesn't resolve.
  12. Setuid sudo starts but never becomes root.
  13. The command can't send a signal to your editor.

Drill 2: what would break?

seccomp blocks mount. What would a mount let a command do to Landlock's rules?
Landlock can't be switched off. Its rules are tied to places in the file tree, so the danger is rearranging that tree.
Why does no_new_privs come before both installs?
Without it (or root's CAP_SYS_ADMIN), the kernel refuses both seccomp and Landlock. sandbx sets it first so the error is reported clearly.
Why is memfd_create on seccomp's list?
Landlock matches on paths. A file that lives only in memory gives it nothing to match.
io_uring would slip past which lock, and why?
The trap from the walkthrough. Landlock still checks the file, wherever the request came from. seccomp is the one that never sees the work.
Which namespaces does every sandboxed command get, whatever the policy?
User lets sandbx create the others without root, and PID gives lifetime and signalling. Network is dropped when network is granted; mount appears only with --allow-dns.

One version

They cover each other's blind spots. Namespaces give the command a private copy of the network and process table, so there's nothing to connect to and nothing outside to signal. Landlock decides which files and TCP ports it may touch, but its rules hang off the file tree and only cover TCP. seccomp removes whole kinds of request: mounts that would rearrange that tree, path-less memory files, UDP, io_uring, which would do work behind seccomp's own back, and creating new namespaces. Neither of the last two installs without no_new_privs, so that's set first.
