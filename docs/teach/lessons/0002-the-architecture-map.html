The architecture map

Six layers in one binary

sandbx ships as one binary built from 28 small crates. They sort into six layers. You do not need all 28 names for an interview. You need the layers, and one crate per layer to point at.

LayerCrate to nameIts job
Front endsandbx-cliThe subcommands (sandbox-run, agent-run, tui, auth, hash). Four more crates run the terminal screen. One of them, sandbx-text, strips control characters from the model's text so it can't take over your terminal.
Turn loopsandbx-turnRounds of "ask the model, run what it asked for". sandbx-approval defines the gate it asks first.
Modelsandbx-anthropicA hand-written streaming HTTP client. Four small crates hold the request and response vocabulary around it.
Toolssandbx-toolsThe seven tools, as a closed list: nothing can add a tool at runtime.tools/lib.rs:5
Sandboxsandbx-coreThe enforcement. sandbx-grants turns flags into a policy first.

Three more crates are test fixtures that never ship. The full list is on the architecture cheat sheet.

Two roads to your files

This is the most important picture in the codebase. The tools split into two groups, and each group passes a different check.

The left road. read, write, edit, ls, grep and find are Rust functions running inside sandbx. The kernel's sandbox features only restrict a process that has been locked, and sandbx itself is not locked. So these six get a check written in sandbx's own code, FsGuard. It is their only filesystem protection.guide-sandboxing:36

The right road. bash runs an arbitrary shell command, so it gets the strong walls: the kernel's. sandbx starts a fresh copy of its own binary, the helper. The helper locks itself and then runs the command.

Why the two roads can't disagree. Both read their answers from one table in sandbox_policy.rs. Add a kind of grant and the compiler points at every place that must handle it.guide-sandboxing:15

Analogy: why a copy locks itself

Picture a hotel safe that locks only from the inside, and once locked never opens again. You can't climb in yourself, because you still have work to do outside: talk to the model's API and save the conversation. So you send in a copy of yourself, and it locks the door behind it.

That is the helper. The kernel's locks are one-way: once a process applies them, it can never remove them, and every process it starts inherits them. sandbx's own header says it in one clause: the locks are applied by a re-exec'd helper to itself so sandbx is not.core/lib.rs:5 ("Re-exec" means a program starting a new copy of itself.)

The copy is the same binary. The first thing main does is check whether it was started as the helper, before it even parses flags.main.rs:23 Lesson 4 opens the helper up.

The checks before any road

The turn loop runs two checks before a call reaches the tools. The first: is the requested tool one this turn actually offered? If not, it is refused before the gate is even asked. Otherwise an allow-everything gate could run a bash the operator never offered.approval-gate:25 The second is the gate itself, CallGate::approve. The front end supplies it: agent-run and tui each have their own.

The gate is asked before the tool starts, never while it runs. A write can't be stopped halfway, so a "no" given while it runs would arrive after the file had already changed.approval-gate:14

Likely question: "Why 28 crates for one binary?"

Because which crate depends on which is a security property here, and the build checks it:

  • deny.toml lists which crate may depend on which. Only sandbx-anthropic, the one crate that talks to the model over the network, may use the HTTP library.deny.toml:35
  • Starting a process is a lint error everywhere except sandbx-core, so a new spawn site that skips the sandbox fails the build.clippy.toml:8

Then add the honest limit, which SECURITY.md states itself: this is convention plus tooling, not a hard guarantee. It only sees sandbx's own code, so a dependency that starts a process does it unseen.SECURITY:270

Check yourself

The grep tool reads a file. What checks that the path is allowed?
grep is a Rust function and starts no process, so the kernel's locks never see it. FsGuard is its only filesystem check.
In shipped code, which crate is allowed to start a subprocess?
clippy.toml bans Command::new everywhere. spawn::command in sandbx-core holds the only exception in code that ships. The bash tool asks sandbx-core to spawn for it.
Why does a helper copy apply the kernel locks, rather than sandbx itself?
The locks are one-way and inherited. sandbx still needs to reach the model's API and save sessions, so it sends a copy in to lock itself.
The model asks for bash, but this turn only offered read and ls. What happens?
The turn loop checks the call against the offered tools first. The gate only ever sees calls that were on the table.

Which versus where. If that took effort to recall, good: the effort is what makes it stick.

Your win: trace one bash call

Without scrolling up, click the steps in the order they happen. A wrong pick flashes red and stays put.

  1. The CLI parses the flags, and sandbx-grants turns them into a policy
  2. sandbx-turn sends the prompt via sandbx-anthropic and streams the reply
  3. The reply asks for bash; the loop checks this turn offered it
  4. The gate's approve decides whether this one call may run
  5. sandbx-tools builds /bin/sh -c "…" as a sandboxed command
  6. sandbx-core starts a fresh copy of the sandbx binary as the helper
  7. The helper locks itself with the kernel's features, then runs the shell
  8. The output goes back to the model; audit records go to stderr
